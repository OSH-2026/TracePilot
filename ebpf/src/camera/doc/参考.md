# TracePilot 参考文档总结
**文档时间**：2026-05-11

## 一、项目定位
TracePilot 是一个面向 Android 交互负载的、以帧为对齐单位、具备依赖感知能力的调度辅助系统（Frame-aligned, dependency-aware scheduling assistant for Android interaction workloads）。

**核心目标**：在 Pixel 6a 设备上，通过 eBPF 采集进程级调度事件，利用机器学习建模并进行针对性调度策略干预（hint），以验证相比默认调度器的改进效果。

## 二、核心设计理念：从 PID-Centric 到 Frame-Centric
### 2.1 PID-Centric 方案为何不可行
1. PID 不稳定：同一 App 每次启动 PID 不同，一个 App 可能有多个进程（主进程、WebView/渲染进程、推送进程、远程 service 进程），PID 还会被系统复用。PID 只能代表一次进程实例，无法代表 App、会话或用户行为。
2. 卡顿不是单个 PID 的问题：Android jank 的根因通常是 UI thread、RenderThread、Binder 线程、system_server、SurfaceFlinger 之间的等待链——涉及 futex、CPU 频率、内存回收、I/O 等多个因素形成的依赖关系。
3. eBPF 只能观测内核事件：eBPF 适合作为系统证据层，观察调度、唤醒、Binder 通信、futex 等待等，但它无法直接回答“用户在经历什么”。

### 2.2 正确的路径：Frame-Centric + Dependency-Centric
- 用 Perfetto FrameTimeline 定位 jank frame，获取 frame token、expected/actual timeline、jank type 作为 ground truth
- 在 frame window 内通过 eBPF 采集调度、唤醒、Binder、futex、CPU 频率、内存回收等系统证据
- 构建依赖关键路径图（Critical Path Graph），识别 UI thread、RenderThread、Binder server、system_server、SurfaceFlinger 与资源状态之间的依赖链

**核心原则**：
FrameTimeline 定义问题，eBPF 提供原因，Graph 找关键路径，Hint Engine 仅做受控的临时干预。

## 三、身份模型层次
架构应采用以下层次模型，放弃以 PID 为核心的建模方式：
`User Interaction → App package / UID → App Session / Activity / Window → Frame token → Process instance → PID / TID`

- **App 标识**：Android 为每个 App 分配唯一 UID，适合作为系统级稳定标识
- **进程实例标识**：ProcessInstanceId = boot_id + pid + start_time_ns + uid + process_name
- **线程角色推断**：结合 comm、tid、call pattern、frame overlap、binder role、sched behavior、Perfetto slice 等综合推断 UI thread、RenderThread、Binder client/server、SurfaceFlinger、Background worker 等角色

## 四、Frame-Centric 可观测性架构
### 4.1 交互窗口定义
`Interaction Window = [frame_expected_start - pre_margin, frame_actual_end + post_margin]`

在此窗口内采集和聚合：
- UI thread 是否 runnable 但没有 CPU
- RenderThread 是否等待 UI thread
- Binder 调用是否阻塞
- system_server 是否延迟响应
- SurfaceFlinger 是否为瓶颈
- 是否存在 futex 等待
- 是否存在内存回收 / I/O / CPU 降频

### 4.2 三层数据模型
| 层级 | 内容 | 说明 |
| --- | --- | --- |
| 上层 | FrameKey ( package_name, uid, process_upid, frame_token, expected_ts, actual_ts ) | 以帧 / 交互为基本单元 |
| 中层 | App Session / Frame Token / UID | 语义聚合层 |
| 底层 | ThreadKey ( boot_id, pid, tid, uid, start_time_ns, comm ) | eBPF 采集的原始调度事件 |

通过 user-space resolver 完成映射：`FrameKey -> AppSession -> UID -> ProcessInstance -> TID`

### 4.3 eBPF 采集内容
#### 基础观察（Step 1）
- sched_switch / sched_wakeup：wakeup-to-run latency、runnable delay
- binder_transaction / binder_transaction_received：Binder 通信延迟和等待时间
- futex wait / wake：锁等待分析
- cpu_frequency：CPU 频率与大小核信息

#### 增强观察（Step 2）
- memory reclaim(mm_vmscan_direct_reclaim_begin/end)
- page fault
- block I/O(block_rq_issue/complete)
- thermal throttling
- SurfaceFlinger / RenderEngine 调度

## 五、交互关键路径图（Interaction Critical Path Graph）
### 5.1 图节点
Frame node、UI thread node、RenderThread node、Binder client/server thread、system_server thread、SurfaceFlinger main thread、futex wait node、CPU resource node、memory reclaim node、I/O wait node

### 5.2 图的边及权重
- **边类型**：WAKEUP、RUNNABLE_WAIT、BINDER_CALL、FUTEX_WAIT、CPU_RUN、PREEMPTED_BY、FRAME_DEPENDENCY、RESOURCE_STALL
- **权重指标**：duration_ns、p95_ns、count、critical_window_overlap_ratio、jank_overlap_score

### 5.3 关键线程评分模型
```
CriticalScore(tid) = + b * runnable_delay_p95
                    + a * frame_window_overlap
                    + c * binder_dependency_centrality
                    + d * futex_wait_contribution
                    + e * render_path_proximity
                    + f * repeated_jank_cooccurrence
                    - g * background_penalty
```
重点关注：frame_window_overlap、render_path_proximity、binder_dependency_centrality（目标是用户体验，而非平均 CPU 利用率）。

## 六、安全 Hint 引擎
### 6.1 Hint 类型
- BOOST_THREAD：提升线程优先级
- PIN_TO_BIG_CORE_SHORT：短暂固定到大核
- PROTECT_UI_CHAIN：保护 UI 依赖链
- LOWER_BACKGROUND_COMPETITOR：降低后台竞争
- UCLAMP_MIN_TEMPORARY：临时 uclamp 下限
- NOOP：空操作

### 6.2 Hint 规范
```json
{
    "hint_id": "h_001",
    "type": "BOOST_THREAD",
    "target": {
        "uid": 10172,
        "tid": 28431,
        "role": "RenderThread"
    },
    "ttl_ms": 300,
    "uclamp_min": 384,
    "reason": "RenderThread wakeup-to-run p95 exceeded frame budget",
    "rollback": "auto_after_ttl"
}
```

### 6.3 安全边界
#### 允许
- 前台 App UID
- RenderThread / UI thread / 已确认 Binder 依赖链上的服务线程
- 带 TTL
- 临时 uclamp
- 可回滚
- 记录审计日志

#### 禁止
- 直呼 PID boost
- 无 TTL hint
- 模糊/无差别调度策略
- 直接杀进程
- 修改 system_server 全局参数

## 七、Inference-Aware（推理感知）调度
### 7.1 推理负载识别
观察 NNAPI / GPU / CPU 推理线程的特征（CPU burst pattern、thread name、process package、known inference app、memory bandwidth proxy、thermal state），以 proxy 方式间接感知，不直接依赖 NPU/GPU 细节。

### 7.2 冲突场景与策略
| 场景 | 策略 |
| --- | --- |
| 前台 UI + 后台推理 | 临时 boost UI chain |
| 前台推理 + UI | 对推理线程限额，保证 UI |
| 后台推理 | 降低优先级 |
| 用户等待推理结果 | 对推理线程做 deadline-aware boost |
| 热/功率压力 | 熔断（circuit breaker），暂停 hint 干预 |

### 7.3 资源预算
每个 hint 需要计入：interaction_budget、inference_budget、thermal_budget、battery_budget，防止“一直 boost”。

## 八、系统架构总览
1. Ground Truth Layer：Perfetto FrameTimeline / jank / frame token
2. Semantic Identity Layer：package / UID / session / process instance / role
3. eBPF Evidence Layer：sched / wakeup / binder / futex / freq / reclaim
4. UI / Render / Binder / SurfaceFlinger / Resource Critical Path Graph Builder：frame-window dependency graph
5. ML / Heuristic Ranking Layer：critical thread score / jank cause classification
6. Safe Hint Engine：whitelist / TTL / rollback / budget / audit
7. User-space Actuator：uclamp / affinity / cgroup / priority hint

## 九、分阶段实施路线
### Step 1：基础管线
1. Perfetto FrameTimeline 采集 jank ground truth
2. eBPF 采集 sched_switch / sched_wakeup
3. UID/package/session/process resolver
4. frame window 内 runnable delay 聚合
5. UI/RenderThread 角色识别
6. 输出 top-k critical threads
7. 用户态临时 hint（带 TTL 和 rollback）

### Step 2：增强
1. Binder dependency graph
2. futex wait graph
3. CPU frequency / big-little 分析

5. 干预模式对比实验

### Step 3：研究前沿
1. inference-aware scheduling
2. memory reclaim / I/O / thermal 分析
3. multi-window / multi-app 竞争
4. learned policy / bandit 策略
5. Cuttlefish / sched_ext 实现

## 十、关键结论
1. eBPF + PID-centric 方案不可行，必须转向 Frame-centric + Dependency-centric。
2. Ground truth 是 Perfetto FrameTimeline（jank frame token、expected/actual timeline），而非某个 PID 的 runnable_delay。
3. 语义建模应以 UID/package/session/process instance/thread role 替代 PID。
4. eBPF 的定位是：在 frame window 内采集依赖图证据，而非全局 PID 事件查询。
5. Hint 必须安全：白名单、TTL、可回滚、审计日志。
6. TracePilot 最终应成为 AI-OS 的 Interaction-Aware Scheduling Assistant——内核观测 + 理解用户体验 + 关键路径分析 + 受控 hint 干预，在短时间窗口内提升响应性。
