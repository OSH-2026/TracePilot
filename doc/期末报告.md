## 1. 项目概述

### 1.1 项目背景

Android 系统的 UI 卡顿（Jank）是影响用户体验的核心问题。传统的性能分析以进程（PID）为中心，但 PID 具有不稳定性（跨运行变化、被多进程共享、可被回收），而 Android 卡顿的根本原因通常是 UI Thread、RenderThread、Binder、system_server、SurfaceFlinger 之间的复杂等待链，无法通过单一 PID 定位。

### 1.2 项目目标

TracePilot 是一个**以帧为中心、依赖感知的 Android 调度辅助系统**，核心能力包括：

- **检测**：基于 Perfetto FrameTimeline 建立卡顿真值标准
- **诊断**：通过 eBPF 采集内核调度事件，构建帧内依赖图，定位瓶颈线程
- **干预**：通过安全提示引擎生成可控的调度优化建议

### 1.3 解决方案路径

```
Perfetto FrameTimeline（定义"哪里出了问题"）
    → eBPF（采集"为什么出问题"）
    → Critical Path Graph（找出瓶颈）
    → Safe Hint Engine（受控干预）
```

### 1.4 目标平台

- **设备**：Google Pixel 6a（已解锁并 Root，Magisk）
- **系统**：Android 14，Kernel 6.1，启用 BTF
- **团队**：潘智勇、李松茂、邵晨轩、贺小轩、杨子皓

## 2. 架构设计

### 2.1 六层架构

TracePilot 采用分层架构设计，各层职责明确、松耦合：

| 层 | 名称 | 职责 |
|---|------|------|
| 1 | **真值层（Ground Truth）** | Perfetto FrameTimeline — 定义卡顿真值（哪些帧未按时完成） |
| 2 | **语义标识层（Semantic Identity）** | 将内核 TID 映射为应用包名/UID/Session/进程实例/线程角色 |
| 3 | **eBPF 证据层（Evidence）** | 采集 `sched_switch`、`sched_wakeup`、`binder`、`futex`、`cpu_frequency`、`reclaim` 事件 |
| 4 | **关键路径图构建层（Critical Path Graph）** | 构建帧窗口依赖图，包含 17 种节点和 12 种边 |
| 5 | **ML/启发式排序层（Ranking）** | 计算 CriticalScore 线程排名和卡顿根因分类 |
| 6 | **安全提示引擎（Safe Hint Engine）** | 生成带白名单/TTL/回滚/预算/审计约束的优化建议 |


### 2.2 端到端数据流水线

```
Step 1: Docker 容器中交叉编译 eBPF 探针 + 加载器（NDK + clang）
Step 2: 部署到 Pixel 6a（adb push）
Step 3: 并行启动 Perfetto 后台追踪 + eBPF 采集（30～60 秒）
Step 4: 拉取数据（adb pull events.bin + .perfetto-trace）
Step 5: 离线分析
   ├── trace_processor_shell SQL → 帧边界与卡顿标签（frames.txt）
   ├── Python 分析脚本 → CriticalScore 排名、Binder/Futex 图、CPU 频点归因
   ├── Jank 分类器 → 11 类根因分析
   └── 图导出 → DOT/SVG 可视化
Step 6: 多轮对比与报告生成
Step 7: Safe Hint Engine 生成部署命令
```

### 2.3 帧对齐技术（核心创新）

TracePilot 的核心创新在于**帧对齐**——在统一时钟域上将 eBPF 内核调度事件与 Perfetto 用户空间帧边界精确匹配：

1. **时间域对齐**：eBPF 与 Perfetto 均使用 `CLOCK_MONOTONIC`，同一时间域
2. **帧窗口匹配**：对每个 Perfetto 帧，定义 `Frame Window = [expected_VSYNC, actual_presentation_time]`，该窗口内所有 eBPF 调度事件归属该帧
3. **线程聚合与评分**：按帧窗口聚合线程级指标，使用加权公式计算

### 2.4 关键路径图（ICPG）设计

#### 17 种节点类型

| 节点类型 | 含义 |
|---------|------|
| Thread | 通用线程节点 |
| Frame（SF/VD/VF/AP） | SurfaceFlinger/VD/VF/App 帧 |
| RenderThread | 渲染线程 |
| UI Thread | 主线程 |
| Binder Proxy | Binder 代理节点 |
| Video Decoder | 视频解码器 |
| Buffer Queue | 缓冲区队列 |
| Network Socket | 网络套接字 |
| CPU Core | CPU 核心 |
| IRQ Vector | 中断向量 |
| Thermal Sensor | 温度传感器 |

#### 12 种边类型

| 边类型 | 含义 |
|--------|------|
| WAKEUP | 唤醒关系 |
| RUNNABLE_WAIT | 就绪等待 |
| BINDER_CALL | 跨进程 Binder 调用 |
| FUTEX_WAIT | 锁竞争等待 |
| CPU_RUN | CPU 执行 |
| PREEMPTED_BY | 被抢占 |
| FRAME_DEPENDENCY | 帧间依赖 |
| RESOURCE_STALL | 资源停滞 |
| DECODE_DEPENDENCY | 解码依赖 |
| BUFFER_QUEUE | 缓冲区队列堵塞 |
| THERMAL_STALL | 温控降频停滞 |
| NETWORK_WAIT | 网络等待 |

#### 图构建流程

8 阶段构建：调度唤醒边 → Binder 边 → Futex 边 → CPU 频点边 → 内存边 → 帧依赖边 → 窗口重叠聚合 → 卡顿共现/后台惩罚

## 3. 技术细节

### 3.1 技术栈总览

| 类别 | 技术选型 |
|------|---------|
| **编程语言** | C（BPF 内核探针 + 用户态加载器）、Python（分析/可视化/训练）、SQL（Perfetto 轨迹分析） |
| **内核技术** | eBPF（最多 13 个 tracepoint）、BPF CO-RE、BPF Ring Buffer（16MB+4MB+4MB）、BPF Hash Maps |
| **构建系统** | GNU Make + Docker（ubuntu:22.04 基础镜像）+ clang 交叉编译 |
| **交叉编译** | Android NDK r26b（目标 `aarch64-linux-android`）、libbpf v1.4.7、elfutils 0.191、bpftool |
| **追踪框架** | Perfetto（128MB ring buffer、trace_processor_shell SQL 引擎、atrace + ftrace） |
| **图算法** | Brandes betweenness centrality（k 采样）、多源 BFS |
| **机器学习** | scikit-learn DecisionTreeClassifier（CART，max_depth=5），6 维特征嵌入 |
| **可视化** | Graphviz DOT 格式、SVG 导出 |

### 3.2 eBPF 探针设计

TracePilot 在不同场景部署不同探针组合，最大部署 13 个探针（Camera 场景）：

| 类别 | 探针 | 目的 |
|------|------|------|
| 调度 | `sched_switch`、`sched_wakeup` | 唤醒到运行延迟、就绪延迟 |
| Binder IPC | `binder_transaction`、`binder_transaction_received` | 跨进程调用依赖 |
| Futex | `sys_enter`/`sys_exit`（NR_futex=98） | 锁竞争分析 |
| CPU 频率 | `cpu_frequency` | 大小核集群分析 |
| 内存 | `mm_vmscan_direct_reclaim_begin` | 内存压力检测 |
| IRQ/SoftIRQ | `irq_handler_entry/exit`、`softirq_entry/exit` | 系统开销归因 |


### 3.3 CriticalScore 评分模型

#### 页面切换场景（7 项）

```
CriticalScore = 0.30 × frame_window_overlap
              + 0.10 × log1p(runnable_delay_ms)
              + 0.25 × binder_dependency_centrality
              + 0.10 × futex_wait_contribution
              + 0.20 × render_path_proximity
              + 0.05 × repeated_jank_cooccurrence
              - 0.05 × background_penalty
```

#### 视频浏览场景（10 项）

在页面切换模型基础上增加：
```
+ 0.20 × decode_path_proximity
+ 0.10 × thermal_proximity
+ 0.15 × buffer_underrun_contribution
- 0.05 × network_penalty
```

#### Camera 场景（5 项简化版）

使用 `frame_window_overlap`、`runnable_delay`、`binder_centrality`、`futex_wait_norm`、`render_path_proximity`，带 `-0.05` 后台惩罚。

### 3.4 Jank 根因分类器（11 类）

| 分类 | 判定条件 |
|------|---------|
| `RUNNABLE_DELAY` | 线程就绪延迟 P95 > 阈值 |
| `BINDER_BLOCKING` | Binder 边中心性 > 阈值 |
| `FUTEX_BLOCKING` | Futex 边贡献 > 阈值 |
| `CPU_CONTENTION` | 所有核心利用率 > 阈值 |
| `THERMAL_THROTTLE` | 温控降频分数 > 阈值 |
| `DECODE_LATE` | 解码边延迟 > 阈值 |
| `BUFFER_UNDERRUN` | 存在缓冲区队列边 |
| `NETWORK_WAIT` | 存在网络延迟边 |
| `MEMORY_PRESSURE` | 检测到内存回收事件 |
| `SYSTEM_IRQ` | IRQ/SoftIRQ 频率过高 |
| `UNKNOWN` | 无明显信号 |

### 3.5 安全提示引擎（Safe Hint Engine）

#### 5 种提示类型

| 提示类型 | 描述 | 安全约束 |
|---------|------|---------|
| `BOOST_THREAD` | 临时提升 RenderThread/UI 线程优先级 | TTL 300ms |
| `PIN_TO_BIG_CORE_SHORT` | 临时绑定大核心 | 短时限制 |
| `PROTECT_UI_CHAIN` | 保护 Binder 依赖链 | 仅前台应用 |
| `LOWER_BACKGROUND_COMPETITOR` | 降低后台竞争 | 不涉及系统服务 |
| `UCLAMP_MIN_TEMPORARY` | 临时最小利用率钳制 | TTL 限制 |

#### 安全规则

- 仅允许前台 App UID 的目标线程
- 仅允许 RenderThread/UI Thread/已确认 Binder 链
- 禁止直接提升 PID、禁止无限 TTL、禁止修改 system_server 全局参数
- 所有提示记录审计日志

### 3.6 学习型策略（Task 17）

- **算法**：scikit-learn DecisionTreeClassifier（CART），`max_depth=5`，`min_samples_leaf=2`，`class_weight=balanced`
- **特征维度**：6 维（runnable_delay、binder_centrality、futex_wait、thermal_throttle、decode_late、system_irq）
- **结果**：96 个训练样本 100% 准确率，决策边界 `runnable_delay ≤ 12.13 → CPU_CONTENTION，否则 → THERMAL_THROTTLE`
- **部署**：导出为 C 头文件 `learned_model.h`，包含 `learned_predict()` 内联函数

### 3.7 Pipeline 策略对比

三种离线策略对比评估：

| 策略 | 方法 | 评价 |
|------|------|------|
| `cpu_only` | 按 CPU 时间选择线程 | 单一维度，精度低 |
| `latency_only` | 按就绪延迟选择线程 | 忽略依赖关系 |
| `pipeline_critical_score` | 多维图感知综合 | 持续最优 |

### 3.8 关键工程挑战

1. **自定义 sched_switch 修复**：Pixel 6a 的 `vmlinux.h` 中 `prev_state` 字段为 8 字节 `long`，但实际应为 4 字节 `unsigned int`，需要本地结构体定义修正
2. **内核内延迟计算**：在 BPF 程序内部计算唤醒延迟和抢占延迟，减少一半 ring buffer 事件量
3. **FrameTimeline 回退机制**：当应用特定 FrameTimeline 不可用时，回退到 SurfaceFlinger 侧帧数据并标注证据质量限制

## 4. 数据测试分析

### 4.1 测试场景总览

TracePilot 在 Pixel 6a（Android 14，Kernel 6.1）上对 5 个真实 Android 交互场景进行了系统性的数据采集与分析，覆盖页面切换、视频浏览、信息流滚动、游戏和拍照五类典型用户场景。

|------|---------|---------|---------|--------|------|
| **页面切换** | QQ/微信/小红书/抖音间来回切换 | Perfetto + eBPF（13 探针）两轮采集 | 2171 / 1271 帧 | 72.5%~96.6% | RUNNABLE_DELAY + THERMAL_THROTTLE |

### 4.2 场景一：页面切换

#### 4.2.1 场景介绍与测试方法

**场景描述**：页面切换是 Android 用户最频繁的交互操作之一，涉及 Activity 生命周期切换、View 重绘、SurfaceFlinger 合成等多层协作。本场景在 QQ、微信、小红书、抖音四款应用之间来回切换，观察过渡帧的调度特征。

**测试目的**：对比页面切换场景下调度瓶颈、依赖图特征和温控影响，验证 TracePilot 13 探针增强版的分析能力。

**测试方法**：在 Pixel 6a 上进行两轮独立采集（Run 1 和 Run 2），均在多应用之间快速切换。每轮部署 13 个 eBPF 探针（sched + Binder + Futex + CPU 频率 + 温控 + 内存回收 + IRQ/SoftIRQ），同步采集 Perfetto FrameTimeline 和 ftrace 系统事件。

**两轮采集配置**：

| 配置项 | Run 1 | Run 2 |
|--------|-------|-------|
| Session ID | `6edbc3e2-...-104731` | `93d39f8a-...-106833` |
| events.bin 大小 | 690 MB | 459 MB |
| sched 事件数 | 5,859,276 | 3,958,504 |
| 增强事件数 | 522,760 | 365,290 |

#### 4.2.2 核心指标对比

| 维度 | Run 1 | Run 2 | 变化分析 |
|------|:---:|:---:|------|
| 总帧 / Jank | 2171 / 1575 | 1271 / 1228 | Run 2 帧数减少但 Jank 率升高 |
| **Jank 率** | **72.5%** | **96.6%** | +24.1pp，设备温控降频导致恶化 |
| 图规模 | 6968 节点 / 5234 边 | 4799 节点 / 3106 边 | 边密度相近 |
| BINDER 边 | 52 | 53 | Binder 交互量稳定 |
| FUTEX 边 | 2371 | 1770 | 锁竞争略有减少 |
| CPU | little 1.67 / big 2.09 GHz | little 1.64 / big 2.05 GHz | 同水平 |
| freq_throttle_ratio | 0.00 | **0.47** | **Run 2 出现温控降频** |
| Thermal | neutral 31.4°C | VIRTUAL-SKIN 36.8→41.5°C | **温度显著上升** |

> Jank 率极高（72.5%~96.6%）的背景说明：多应用快速切换产生大量合成过渡帧，Perfetto FrameTimeline 将这些未完成/过渡帧也计入 deadline_missed，因此 Jank 率不等同于"用户感知卡顿率"，更适合作为相对对比指标。

| 边分布 | BINDER=52, FUTEX=2371, RESOURCE_STALL=51, NETWORK=19 |
| Inference | dominant=RUNNABLE_DELAY, recommended=BOOST_THREAD, confidence=0.9999 |

**Top-5 嫌疑线程**：

| # | TID | comm | CriticalScore | 主因 |
|---|-----|------|:---:|------|
| 1 | 103 | — | 0.825 | RUNNABLE_DELAY |
| 2 | 52 | rcuop/4 | 0.567 | RUNNABLE_DELAY |
| 3 | 66 | rcuop/6 | 0.473 | RUNNABLE_DELAY |
| 4 | 48 | — | 0.459 | RUNNABLE_DELAY |

**Jank 分类**：全部 1575 帧 → RUNNABLE_DELAY
**Hint**：1 条 PROTECT_UI_CHAIN → surfaceflinger（TID 686），TTL 300ms

| 对比维度 | 主要差异 |

### 4.3 场景二：视频浏览

#### 4.3.1 场景介绍与测试方法

**场景描述**：视频浏览涉及硬件解码器（VD）、缓冲区队列和网络加载等独特瓶颈，与纯 UI 页面切换有本质不同。本场景在抖音 App 中播放视频内容，测试 TracePilot 对视频特有依赖链路的捕获能力。

**测试目的**：验证增强版 eBPF 探针对视频解码依赖边（DECODE_DEPENDENCY）、缓冲区队列（BUFFER_QUEUE）和网络等待（NETWORK_WAIT）的检测能力，并评估温控保护对 Hint 引擎的正确干预。

**测试方法**：与页面切换同批采集（同一设备同一次操作），部署 13 个 eBPF 探针，视频解码器识别 3 个。

| 配置项 | 数值 |
|--------|------|
| Session ID | `93d39f8a-...-107983` |
| events.bin 大小 | 451 MB |
| sched 事件数 | 3,598,368 |
| 增强事件数 | 567,918 |
| 视频解码器 | 3 个已识别 |
| 锚定 App | com.ss.android.ugc.aweme（抖音） |

#### 4.3.2 核心指标

| 指标 | 值 | 与页面切换对比 |
|------|-----|--------------|
| 总帧 / Jank | 2141 / 1524（71.2%） | 帧数更多但 Jank 率稍低于 Run 2 |

| little | 1,357,043 kHz | 1,446,501 kHz | surfaceflinger 主要在此 |
| middle | 1,687,924 kHz | 1,997,836 kHz | UnityMain/GfxDeviceW |
| big | 2,296,805 kHz | 2,187,589 kHz | UnityMain/GfxDeviceW |

> **UnityMain 和 UnityGfxDeviceW 100% 运行在 middle/big cluster**，调度器已经正确将游戏渲染线程分配至性能核心。

#### 4.5.11 场景关键结论

1. **采集能力已验证**：TracePilot 在真实王者荣耀对局中稳定采集 59.2s，产出线程级指标、依赖图和 Jank 分类
2. **负载高度集中**：UnityMain + UnityGfxDeviceW 占对局 on-CPU 的 81.3%，是绝对的核心线程
3. **Futex 锁竞争密集**：52.8 万次 Futex Wait，其中 UnityMain 独占 22.2 万次（42%），说明游戏内使用了大量锁同步
4. **丢帧率极低**：0.22%（2/923），游戏本身帧调度优良，不作为典型的卡顿优化场景
5. **Binder 交互偏少**：仅 36 条 BINDER_CALL 边（vs 399 条 FUTEX_WAIT），游戏主要使用自定义通信
6. **已知限制**：FrameTimeline 使用 SurfaceFlinger fallback，非游戏进程精确绑定；包名自动识别有 `com.luna.music` 误判

### 4.6 场景五：拍照（Google Camera）

#### 4.6.1 场景介绍与测试方法

**场景描述**：Google Camera 是 Pixel 设备上计算摄影的核心应用，拍照过程涉及 ISP（图像信号处理器）、GCam 图像处理线程池、Mali GPU 驱动、YUV 格式转换、JPEG 编码等多层管线。由于 Pixel 使用私有 GSLCamera 栈，标准的 `camera`/`hal` atrace 类别不产生数据，需要通过 eBPF 侧调度事件和 Perfetto SurfaceView 切片间接捕获管线阶段。

**测试目的**：验证 TracePilot 在相机场景下的全自动 9 步分析管线，利用 13 个 eBPF 探针（含 IRQ/SoftIRQ/内存回收）实现多维度根因归因和 9 维 Jank 分类。

**测试方法**：在 Pixel 6a（Android 15，Magisk root）上打开 Google Camera v9.x，执行拍照、切换模式（人像/普通/HDR）等操作，采集 30 秒。通过 `auto_run.py` 一键完成编译→部署→采集→拉取→9 步分析→报告的全流程。

**关键工程突破**：
- **内核进程名截断陷阱**：`com.google.android.GoogleCamera` 被截断为 `com.google.andr`（15 字符限制），项目改用以果推因，在 Perfetto 中反查拥有 `App Deadline Missed` 的 UPID 锁定目标应用
- **PID 复用污染**：引入以 UID 与 TGID 为中心的 Identity Layer Filtering，利用 Perfetto 静态血缘排除非目标 UID 的杂音线程

#### 4.6.2 采集规模

| 数据源 | 事件量 | 说明 |
|--------|--------|------|
| sched 调度事件 | 2,051,704 | 含内核内预计算的 runnable_delay |
| binder/futex/CPU/热控 | 452,572 | 含 debug_id 配对的 Binder + Futex 时长 |
| IRQ/SoftIRQ | 2,129,719 | 硬中断 + 软中断，用于系统开销归因 |
| Perfetto 帧 | 16 jank 帧（总 896，卡顿率 1.8%） | FrameTimeline 标注 |

#### 4.6.3 核心发现：100% CPU Scheduling Contention

全部 16 个 jank 帧的根因均为 **CPU Scheduling Contention**，每帧阻塞时延 200ms-632ms：

| 帧 ID | 总阻塞 | 调度排队 | Binder | IRQ | SoftIRQ | CPU 频率 |
|--------|--------|---------|--------|------|---------|----------|
| 3070235 | 547ms | 502ms（92%） | 0 | 23ms | 5ms | 1849 MHz |
| 3081143 | 632ms | 589ms（93%） | 0 | 28ms | 3.5ms | 1959 MHz |
| 3081187 | 547ms | 533ms（97%） | 0 | 7ms | 1.3ms | 2402 MHz |
| 3078159 | 526ms | 498ms（95%） | 0 | 11ms | 1ms | — |
| 3078349 | 455ms | 435ms（96%） | 0 | 9ms | 1.5ms | 2401 MHz |

**关键结论**：
- Binder IPC 延迟为 **0ns**（全部为 0，跨进程通信不是瓶颈）
- IRQ 开销 5-28ms/帧，仅占 2-5%，非主要因素
- CPU 频率 1700-2750 MHz，无降频（温度正常）
- **纯粹是太多线程竞争 CPU 时间**

> 管线阶段的 Futex 活动：1,518 WAIT / 1,514 WAKE — GCam 内部锁竞争激烈。CPU 频率稳定在 2630MHz，无降频。

#### 4.6.7 Jank 分类器结果（9 维加权）

| 分类 | 帧数 | 占比 | 说明 |
|------|:----:|:----:|------|
| **Futex 锁竞争** | 16 | **100%** | 每帧都有大量 Futex 等待（最高 1,518 次） |
| CPU 降频 | 4 | 36% | 部分帧窗口 CPU 频率偏低 |
| Sched 调度 | 1 | 9% | 仅 1 帧被识别为纯调度问题 |

> 虽然每帧都有大量 Futex 等待，但实际阻塞时间主要由调度排队贡献。Futex 竞争是"症状"（大量线程在等待锁），但根因是"太多线程竞争 CPU 时间使得锁持有者也无法及时执行"。

#### 4.6.8 关键路径分析

每帧的关键路径均为**单跳**模式：`Frame ← Thread (RUNNABLE_WAIT)`，未形成多跳依赖链（因 Binder 事件未落入 jank 帧窗口内）。

代表性关键路径（Frame 3081143，总阻塞 632ms）：

```
Frame (App Deadline Missed)
  ↑ RUNNABLE_WAIT 60.6ms
s.nexuslauncher (TID:27108)  ← 系统桌面，最大干扰
  ↑ RUNNABLE_WAIT 41.1ms
GcamTasks:4 p8 (TID:11938)   ← GCam 图像处理
  ↑ RUNNABLE_WAIT 34.7ms
FinishThread (TID:11627)      ← 系统清理线程
```

#### 4.6.9 调优建议与安全评估

| 优先级 | 建议 | 预期效果 | 安全性 |
|:---:|------|----------|--------|
| 🔴 | 限制后台进程 CPU 占用 — `s.nexuslauncher`（Pixel 桌面）是 15/16 帧最大干扰源 | 减少 ~20% 调度竞争 | 低风险，仅对桌面进程施加 cgroup 限制 |
| 🔴 | 适当提升 GCam 线程优先级 — GcamTasks:0-4 在 13/16 帧中高延迟 | 降低拍照延迟感知 | 中风险，需 TTL 限制避免持续高优先级 |
| 🟡 | GCam 内部锁优化 — GcaGeneric 系列线程 Futex 等待 >100 次/帧 | 减少内部锁竞争 | 需要应用层面改动 |
| 🟡 | Mali GPU 调度关注 — `mali_jd_thread` 100% 帧覆盖 + P95=4.4ms | 考虑 GPU 驱动优先级调整 | 较高风险，GPU 驱动全局影响 |

#### 4.6.10 场景关键结论

1. **100% CPU Scheduling Contention**：16 个 jank 帧全部为调度竞争，无 Binder 阻塞、无温控降频、无内存压力
2. **Pixel 桌面是最大干扰源**：`s.nexuslauncher` 在 15/16 帧出现，调度排队 349ms，是单一最大瓶颈
3. **GCam 内部线程池竞争激烈**：5 个 GcamTasks 处理线程合计延迟 566ms，是拍照负载的固有特征
4. **诊断即结论**：不存在 Binder 阻塞或温控降频，系统整体调度策略就是瓶颈——**零调整建议本身就是最清晰的诊断结论**
5. **全自动 9 步管线**：Camera 场景通过 `auto_run.py` 实现了从编译到报告的完全自动化，是 TracePilot 工程成熟度的标志

### 4.7 跨场景综合分析

#### 4.7.1 卡顿率与场景负载关系

| 场景 | 典型 on-CPU/秒 | Jank Rate | 卡顿特征 |
|------|:---:|:---:|------|
| 页面切换 | 低~中 | 72.5%~96.6% | 过渡帧大量 deadline_missed，非用户感知卡顿 |
| 视频浏览 | 中 | 71.2% | RUNNABLE_DELAY + 高温全降频，Hint 全量抑制 |
| 信息流滚动 | 中~高 | 1.36% | Binder 合成路径 + CPU 调度，missed rate 合理 |
| 游戏（王者荣耀） | **高（670ms/s）** | **0.22%** | 游戏引擎调度优化极佳 |
| 拍照（Google Camera） | 高 | 1.8% | 100% CPU_CONTENTION，无 Binder/温控问题 |

> 反直觉发现：**高负载场景（游戏、拍照）的卡顿率反而低于低负载过渡场景**。原因在于：
> - 游戏引擎（Unity）和相机 App 已经对持续高负载做了充分的调度优化
> - 页面切换的"高 Jank 率"主要来自过渡帧的 FrameTimeline 计数方式，不代表用户感知的卡顿
> - 真正的用户感知卡顿集中在**负载突变点**（应用启动、页面首次渲染、温控触发降频）

#### 4.7.2 各场景 Top 瓶颈对比

| 场景 | Top 瓶颈线程 | 瓶颈类型 | 是否可调度干预 |
|------|-------------|---------|:---:|
| 页面切换 | rcuop/rcuog（内核 RCU） | 内核调度 | 否（内核线程不可干预） |
| 视频浏览 | rcuop/rcuog + 温控降频 | 内核调度 + 硬件热保护 | 否（高温下 Hint 须抑制） |
| 信息流滚动 | VizCompositorTh / Compositor / surfaceflinger | Binder 合成 + on-CPU | **是**（渲染链路线程可优化） |
| 游戏 | UnityGfxDeviceW / UnityMain | on-CPU + Futex 锁 | **部分是**（可优化但锁竞争非调度问题） |
| 拍照 | s.nexuslauncher / GcamTasks | CPU 竞争 | **是**（限制后台桌面进程） |

#### 4.7.3 Pipeline CriticalScore vs 简单策略全场景对比

| 场景 | cpu_only 准确率 | latency_only 准确率 | **Pipeline Score** |
|------|:---:|:---:|:---:|
| 页面切换 | 中（选不中内核 RCU） | 低（选不中真实瓶颈） | **高**（内核 RCU + 应用线程） |
| 信息流滚动 | 中（选中合成线程但无延迟信息） | 低（选中 CronetInit 等无关线程） | **高**（CrRendererMain + 全合成链） |
| 游戏 | 中（选中 UnityMain/GfxDeviceW） | 中（跨轮波动大） | **高**（UnityGfxDeviceW 多维度最优） |
| 拍照 | 中（选中 High-CPU 线程但无依赖信息） | 中（漏掉 s.nexuslauncher） | **高**（GCam 链 + GPU + s.nexuslauncher） |

> 在所有场景中，Pipeline CriticalScore 的多维图感知策略一致优于单一维度策略，验证了"依赖图 + 多维评分"的架构设计合理性。
