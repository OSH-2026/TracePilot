## 1. 项目概述

TracePilot 是一个面向 Android 系统的端到端卡顿（Jank）诊断工具。它通过 **eBPF** 在内核态采集调度与同步事件，结合 **Perfetto** 帧时间线（Frame Timeline）提取帧窗口，在用户态构建 **交互关键路径图（Interaction Critical Path Graph）**，对线程进行多维加权评分与根因分类，并输出可落地的调度 Hint 建议。

### 1.1 核心能力

| 层级 | 功能 |
|------|------|
| **Step 1** | Perfetto 帧提取 + eBPF 调度事件 + 身份解析（PID/UID/包名）+ Runnable Delay 聚合 + Hint Engine（TTL/Rollback） |
| **Step 2** | Binder/Futex IPC 图 + CPU 频率归因 + Jank 根因分类器 + 启发式对比 |
| **Step 3** | 温控（Thermal）深化 + 多信号 Inference 证据链融合 + 多会话（Multi-session）对比 |

### 1.2 设计目标

- **双场景覆盖**：页面切换（UI 帧 vsync 超时）与视频浏览（解码丢帧 + 温控降频 + GPU 停滞）
- **端到端自动化**：一键部署采集 → 离线/在线分析 → JSON/SVG 输出
- **可落地的调度建议**：TTL 限时的 Hint，含 Rollback/DRY-RUN 策略
- **可解释性**：每个卡顿帧的证据链（Binder、Futex、Thermal、Runnable Delay 等）

- **模块化设计**：身份层、温控层、推理层、Hint 层各自独立，通过图结构交换数据

## 4. 核心模块详解

### 4.1 eBPF 内核程序 (`bpf/tracepilot.bpf.c`)

内核态程序通过 **13 个 tracepoint** 进行事件采集：

| 类别 | Tracepoint | 采集事件 |
|------|-----------|---------|
| **调度** | `sched_switch` | 上下文切换（含 wakeup latency + runnable delay） |
| **调度** | `sched_wakeup` | 唤醒事件 |
| **中断** | `irq_handler_entry/exit` | 硬中断起止 |
| **软中断** | `softirq_entry/exit` | 软中断起止（含 vec 向量号） |
| **Binder IPC** | `binder_transaction` / `binder_transaction_received` | Binder 调用起止（debug_id 匹配） |
| **Futex** | `sys_enter/sys_exit` | Futex 等待（`__NR_futex=98` 过滤 `FUTEX_WAIT`） |
| **CPU 频率** | `cpu_frequency` | 频率切换事件 |
| **内存压力** | `mm_vmscan_direct_reclaim_begin` | 直接内存回收 |

三个环形缓冲区：
- `events`（16 MB）：调度事件
- `sys_events`（4 MB）：系统中断/软中断事件
- `enhanced_events`（4 MB）：增强事件（Binder/Futex/频率/内存）

### 4.2 用户态加载器 (`loader/main.c`)

1004 行代码，负责：

- **CLI 解析**：`getopt_long` 处理 24+ 命令行参数
- **在线模式**：打开 BPF 骨架、挂载环形缓冲区、轮询采集
- **离线模式**：加载 `events.bin`（v1/v2/v3 格式）、回放分析
- **分析编排**：图模式（`-G`）走完整图管线，非图模式走启发式分析
- **场景路由**：`-s page_switch|video` 或自动检测（`detect_scenario()`）
- **参数默认值**：采集时长 30s，Top-K=10，事件 chunk=65536

### 4.3 图引擎 (`loader/frame_aggregator.c`)

2536 行核心代码，实现完整的图构建与分析管线：

**图节点类型（17 种）：** 线程节点、帧节点（SF/VD/VF/AP）、渲染/UI 线程、Binder 代理、Video Decoder、Buffer Queue、Network Socket、CPU 核、中断向量、IRQ Action、SoftIRQ Action、内存回收、温度传感器

**图边类型（12 种）：** WAKEUP、BINDER_CALL、BINDER_RECEIVED、FUTEX_WAIT、CPU_FREQ、MEM_RECLAIM、FRAME_DEPENDENCY、RENDER_DEPENDENCY、DECODE_DEPENDENCY、BUFFER_UNDERRUN、NETWORK_WAIT、RESOURCE_STALL

**图构建 7 阶段（页面切换）+ 8 阶段扩展（视频）：**

| 阶段 | 内容 |
|------|------|
| Phase 1 | 从调度事件创建线程节点 |
| Phase 1b | 从 Perfetto frame 创建帧节点 |
| Phase 1c | 从系统/增强事件创建资源节点（中断、频率、Binder 代理等） |
| Phase 2 | 构建调度唤醒边（sched_wakeup） |
| Phase 3 | 构建 Binder/Futex/CPU 频率/内存 边 |
| Phase 4 | 帧依赖边 |
| Phase 5 | 帧窗口重叠度 + jank 窗口 runnable delay 聚合 |
| Phase 6 | jank 共现关系 |
| Phase 7 | 后台惩罚（background process penalty） |
| Phase V1–V8 | 视频场景扩展：解码器识别、解码依赖边、Buffer Queue、Network、Thermal 邻近度 |

### 4.4 身份解析 (`loader/identity.c`)

- **Session 标识**：设备 boot_id + 采集时间戳 → 唯一 session_id
- **ProcessInstanceId**：读取 `/proc/<pid>/stat` 获取进程启动时间
- **ThreadKey**：TID + PID + comm
- **包名解析**：`identity_apply_packages_to_graph()` 将 PID 映射到图节点
- **Sidecar 加载**：自动从 `events.bin` 同级目录查找 `identity_map.json`

### 4.5 Hint 引擎 (`loader/hint_engine.c`)

生成 3 类调度 Hint：

| Hint 类型 | 触发条件 | TTL | 作用 |
|-----------|---------|-----|------|
| `HINT_BOOST_THREAD` | CriticalScore > 0.5 且为 Render/UI 线程 | 300ms | nice 优先级提升 |
| `HINT_UCLAMP_MIN_TEMPORARY` | runnable_delay ≥ 5ms 且 render_proximity > 0.3 | 300ms | 最小 utilization clamp |
| `HINT_PROTECT_UI_CHAIN` | UI 链路线程（SurfaceFlinger + App Render + App UI） | 300ms | CPU affinity 保护 |

特性：
- 每个 Hint 含 TTL 与 Rollback 策略（预存原始值，到期恢复）
- 支持 DRY-RUN（仅输出 JSON，不实际下发）与 APPLY（写入 `/proc/pid/task/tid/uclamp.min` 和 `sched_boost`）
- 输出 `hints.json` + `hints_audit.log`

### 4.6 温控分析 (`loader/thermal_profile.c`)

- 从 `thermal_query.sql` 输出加载温度采样序列
- 计算 baseline / peak / jank_delta / throttle_score
- `thermal_profile_apply_to_graph()`：将温控数据注入图节点，更新 `freq_throttle_ratio` 和 `thermal_proximity`
- 无温控数据时回退到 CPU 降频推断

### 4.7 推理引擎 (`loader/inference_engine.c`)

多信号融合推理，每条 jank 帧生成：
- **主假设（hypothesis）**：主导根因
- **次假设（secondary）**：次要因素
- **置信度（confidence）**：0.0–1.0
- **证据链（evidence[]）**：binder_centrality / runnable_delay / thermal_throttle / futex_wait / decode_late / system_irq
- **recommended_hint**：从主导因自动映射到 Hint 类型

### 4.8 多会话对比 (`loader/session_compare.c`)

- 扫描目录下所有 `result.json`
- 解析各会话的快照：jank 率、主因、Top-1 线程
- 构建 Top-1 重叠矩阵
- 输出 `compare_report.json`

### 4.9 分析脚本 (`scripts/`)

| 脚本 | 语言 | 功能 |
|------|------|------|
| `frame_query.sql` | SQL | 提取 SF/VD/VF/AP 四种帧时间线（172 行） |
| `thermal_query.sql` | SQL | 提取温度采样（57 行） |
| `deploy.sh` | Bash | 6 步自动化部署管线 |
| `deploy.ps1` | PowerShell | Windows 宿主部署（WSL 桥接） |
| `trace_features.py` | Python | 从 Perfetto trace 提取原始特征（287 行） |
| `trace_label.py` | Python | 阈值基标注（220 行） |
| `graph_features.py` | Python | 图拓扑特征提取（137 行） |
| `label_jank.py` | Python | 交互式标注工具（148 行） |
| `auto_label.py` | Python | 自动标注（106 行） |
| `train_jank_model.py` | Python | 决策树训练 + C header 导出（228 行） |

## 5. 关键算法

### 5.1 双场景评分公式

#### 页面切换（7 项加权）

```
CriticalScore = 0.30 * frame_window_overlap
              + 0.10 * log1p(runnable_delay_ms)
              + 0.25 * binder_dependency_centrality
              + 0.10 * futex_wait_contribution
              + 0.20 * render_path_proximity
              + 0.05 * repeated_jank_cooccurrence
              - 0.05 * background_penalty
```

#### 视频浏览（10 项加权）

```
CriticalScore = 0.15 * frame_window_overlap
              + 0.10 * log1p(runnable_delay_ms)
              + 0.15 * binder_dependency_centrality
              + 0.05 * futex_wait_contribution
              + 0.10 * render_path_proximity
              + 0.05 * repeated_jank_cooccurrence
              - 0.05 * background_penalty
              + 0.20 * decode_path_proximity
              + 0.10 * thermal_proximity
              + 0.15 * buffer_underrun_contribution
              - 0.05 * network_penalty
```

**设计原则：** 页面切换侧重 Binder IPC 与 Render 路径（UI 响应），视频浏览新增解码路径、温控、Buffer 和网络的权重。

### 5.2 图构建算法

采用 **增量式 7 阶段（+8 视频扩展）** 构建：

1. **Phase 1–1c**：从事件流提取节点（线程、帧、资源），TID→节点索引哈希映射 O(1) 查找
2. **Phase 2–4**：按事件时序构建有向边，避免重复（边去重哈希）
3. **Phase 5**：帧窗口回填 → 计算每个节点在各 jank 帧窗口内的重叠次数
4. **Phase 6**：jank 共现统计 → 同一帧窗口内出现的线程对
5. **Phase 7**：后台惩罚 → 非目标进程线程评分下调

### 5.3 介数中心度（Brandes Betweenness Centrality）

用于量化 Binder 子图中各线程的中介重要性：

- 基于 Brandes 算法，O(VE) 复杂度
- 采用 **k-sampling 优化**：全采样或 min(n, 32) 采样源
- 归一化到 [0, 1]

### 5.4 BFS 邻近度（Render / Decode Proximity）

多源 BFS 计算线程到渲染/解码节点的最短路径距离：

- 渲染源：UI Thread、RenderThread、SurfaceFlinger
- 解码源：MediaCodec 解码器线程
- 距离归一化：`proximity = 1.0 / (1.0 + distance)`

### 5.5 Jank 根因分类器

11 类分类：

| 类别 | 判断条件 |
|------|---------|
| `RUNNABLE_DELAY` | 该帧 jank 窗口内线程 runnable delay P95 > 阈值 |
| `BINDER_BLOCK` | Binder 边中央度 > 阈值 |
| `FUTEX_WAIT` | Futex 边贡献 > 阈值 |
| `CPU_CONTENTION` | 所有核 util > 阈值 |
| `THERMAL_THROTTLE` | throttle_score > 阈值 |
| `DECODE_LATE` | 解码边延迟 > 阈值 |
| `BUFFER_UNDERRUN` | Buffer Queue 边存在 |
| `NETWORK_WAIT` | 网络延迟边存在 |
| `MEMORY_PRESSURE` | 内存回收事件 |
| `SYSTEM_IRQ` | 中断/软中断高频 |
| `UNKNOWN` | 无明确信号 |

### 5.6 启发式对比（Graph vs Heuristic）

`compare_heuristics()` 对比图中 CriticalScore 排名与传统启发式（仅基于帧窗口重叠 + runnable delay 的 P95）排名的重叠度：

- **Precision@K**：Top-K 重叠比例
- **Rank Correlation**：Spearman 秩相关系数

> **状态：** 模型已训练并导出 C header，但**尚未集成**到 loader 的推理引擎中。

#### 7.4.1 背景与目标

将 `inference_engine.c` 中的手写加权规则升级为**数据驱动的机器学习模型**。现有规则使用 10 个加权信号的手写公式：

```
score = 0.30×overlap + 0.10×log1p(rd) + 0.25×binder
      + 0.10×futex + 0.20×render - 0.05×bg
      + 0.20×decode + 0.10×thermal + 0.15×buffer - 0.05×net
```

Task 17 用决策树从标注数据中自动学习分类规则。

#### 7.4.2 技术方案

| 要素 | 技术选型 |
|------|---------|
| **算法** | scikit-learn `DecisionTreeClassifier`（CART 算法） |
| **参数** | `max_depth=5`, `min_samples_leaf=2`, `class_weight=balanced`, `random_state=42` |
| **训练数据** | 3 个 session 共 **96 条**样本（Run 1 / Run 2 / Video） |
| **特征维度** | 6 维：runnable_delay, binder_centrality, futex_wait, thermal_throttle, decode_late, system_irq |
| **类别数** | 10 类（RUNNABLE_DELAY, BINDER_BLOCKING, FUTEX_BLOCKING, THERMAL_THROTTLE, VIDEO_LATE_RENDER, IO_WAIT, MEMORY_RECLAIM, GPU_STALL, AUDIO_SYNC_DRIFT, CPU_CONTENTION） |
| **标签策略** | 基于 trace 原始数据的自动标注（`scripts/trace_label.py`），独立于 Inference 的加权分数 |
| **输出格式** | C 头文件 `learned_model.h`，含 `learned_predict()` 内联函数 |

#### 7.4.3 特征提取与标注

特征从 `result.json` 的 `frame_inferences[].evidence[]` 中按 signal 名称提取权重，缺失特征默认为 0.0，不做归一化。

标注规则（`scripts/trace_label.py`）：

| 条件 | 标签 |
|------|------|
| `thermal_throttle > 0.3` 或 thermal_delta > 2000 mC | `THERMAL_THROTTLE` |
| `binder_centrality > 0.15` | `BINDER_BLOCKING` |
| `futex_wait > 0.15` | `FUTEX_BLOCKING` |
| `decode_late > 0.3` | `VIDEO_LATE_RENDER` |
| `system_irq > 0.3` | `IO_WAIT` |
| 其他 | `RUNNABLE_DELAY` |

#### 7.4.4 训练结果

| 特征维度 | 6 |

| 决策树节点数 | 3 |

#### 7.4.5 学习到的决策规则

```
if runnable_delay ≤ 12.13:
    根因 = RUNNABLE_DELAY（CPU 争用导致线程排队）
else:
    根因 = THERMAL_THROTTLE（温控降频导致性能下降）
```

阈值 12.13 对应约 **180ms** 的原始延迟（`exp(12.13) - 1 ≈ 180ms`）。模型发现：温控降频时 CPU 处理能力下降导致任务堆积，线程 Runnable 队列等待时间显著变长——这一规律比温度读数本身更能区分两种根因。

#### 7.4.6 模型导出（C Header 集成）

```c
// learned_model.h — 决策树结构体数组
static const learned_node_t learned_tree[3] = {
    {0, 12.128f, 1, 2, ...},  // node 0: runnable_delay ≤ 12.13
    {-1, 0.0f, -1, -1, 0, ...}, // leaf: RUNNABLE_DELAY
    {-1, 0.0f, -1, -1, 1, ...}, // leaf: THERMAL_THROTTLE
};

// 预测接口
static inline int learned_predict(const float *features) {
    int node = 0;
    while (learned_tree[node].feature_idx >= 0) {
        if (features[learned_tree[node].feature_idx] <= learned_tree[node].threshold)
            node = learned_tree[node].left;
        else
            node = learned_tree[node].right;
    }
    return learned_tree[node].class_idx;
}
```

#### 7.4.7 与现有规则引擎的对比

| 对比项 | 现有规则（inference_engine.c） | 模型学到的规则 |
|--------|-------------------------------|---------------|
| 判断依据 | 10 个加权信号的加权和 | 仅 `runnable_delay` 一个特征 |
| 阈值 | 无明确阈值，取最高分 | 明确阈值 12.13（≈180ms） |
| 温控判断 | `thermal_throttle > 0.2` 时加 0.5 分 | `runnable_delay > 12.13` 时直接判定 |
| 复杂度 | 多条件嵌套 | 单层决策树（3 节点） |
| 可解释性 | 中等 | 高（1 条规则） |

## 8. 实验数据与分析

### 8.1 实验设置

- **设备**：Google Pixel 6a, Android 14
- **采集时长**：每次 30 秒
- **场景**：页面切换 ×2 次（Run 1 / Run 2），视频浏览 ×1 次
- **分析模式**：`-G -k 10` Graph-based Critical Path

### 8.3 关键发现

**1. Jank 率偏高**

三次采集 Jank 率均在 71%–97% 范围，这与 Pixel 6a 作为中端设备的 CPU/GPU 资源限制有关，也与采集期间刻意触发的高负载场景一致。

**2. 视频场景独有的图特征**

视频浏览场景出现三种页面切换中没有的边类型：
- **DECODE_DEPENDENCY（560 条）**：视频解码器与渲染线程的路径依赖
- **BUFFER_QUEUE（12 条）**：Buffer 队列下溢
- **NETWORK_WAIT（25 条）**：网络读取阻塞

RESOURCE_STALL 在视频场景达到 247 条，是页面切换场景的 5–19 倍，反映视频解码对 CPU/GPU 资源的更强争用。

**3. 温控（Thermal）对 Hint 策略的影响**

| | Run 1 | Run 2 | Video |
|--|:---:|:---:|:---:|
| throttle_score | 0.00 | 0.47 | 1.00 |
| Inference secondary | CPU_CONTENTION | **THERMAL_THROTTLE** | **THERMAL_THROTTLE** |
| recommended_hint | BOOST_THREAD | **UCLAMP_MIN_TEMPORARY** | **UCLAMP_MIN_TEMPORARY** |

当温控介入（Run 2 / Video），Inference 引擎自动将次假设从 CPU_CONTENTION 切换为 THERMAL_THROTTLE，Hint 从 BOOST_THREAD 升级为 UCLAMP_MIN_TEMPORARY。Video 场景 throttle=1.00 时 Hint 被完全抑制，避免在极端温控状态下进一步加重负载。

**4. 跨会话稳定嫌疑线程**

`tid 103` 在三次 session 中均进入 Top-3（Run 1 #1, Run 2 #3, Video #1），`tid 48` 三次均出现在 Top-5，表明存在系统级瓶颈线程。

**5. 图模式 vs 传统启发式**

多会话对比的 Precision@K 指标显示 Run 1 为 0.50，Run 2 和 Video 为 0.70，证明图模式引入的 Binder/Futex/Thermal/Decode 多维信息显著提升了 Top-K 嫌疑线程识别的准确性。

## 9. 已知局限与改进方向

### 9.1 已知局限

| 局限 | 说明 |
|------|------|
| Thermal 数据依赖 | `thermal_query.sql` 依赖 Perfetto trace 中是否含有 thermal 事件，无则回退 CPU 降频推断 |
| Inference 为规则引擎 | 当前基于加权规则融合，非 ML 模型，泛化能力有限 |
| Multi-session 对比粒度 | 目前仅以 Top-1 TID 重叠为主，未做 full Top-K set overlap |
| 单设备验证 | 仅在 Pixel 6a 上验证，未在多样设备/内核版本上测试 |
| BPF 内核依赖 | 需要 BTF 启用 + Root 权限 + kernel 6.1+ |
| Learned Policy 未集成 | Task 17 已训练决策树模型（3 节点、单层、100% 准确率）并导出 `learned_model.h`，但仅覆盖 2 类根因（样本 96 条、类别不均衡），尚未集成到 `inference_engine.c` 中（详见 §7 Step 3+） |

### 9.2 改进方向

1. **ML-driven Inference**：将已训练的决策树模型（`learned_model.h`）集成到 `inference_engine.c`，替换规则引擎
2. **Full Top-K Overlap**：Multi-session 对比扩展为完整 Top-K 集合的 Jaccard 相似度
3. **Cuttlefish 虚拟化部署**：降低对物理设备的依赖，支持 CI/CD 流水线
4. **sched_ext 集成**：在支持 sched_ext 的内核上直接通过 BPF 调度器下发 Hint
5. **多设备验证**：在 Pixel 7/8 系列、不同 Android 版本上验证
