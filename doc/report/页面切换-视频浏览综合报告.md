## TracePilot 分析流水线

整个系统按四个阶段串联，形成"定义问题 → 解释原因 → 定位根因 → 受控修正"的闭环：

### 阶段 1：FrameTimeline 定义问题

Perfetto 录制 Android 帧数据，通过 `frame_query.sql` 提取 **SF（SurfaceFlinger）/ VD（Video Decoder）** 帧时间线。每帧有 `expected_start / expected_end / actual_end` 三个时间戳，若 `actual_end > expected_end` 则标记为 **Jank 帧**。这一步回答"哪些帧卡了"。

| 会话 | SF 帧 | VD 帧 | Jank 帧 | Jank 率 |
|------|:----:|:----:|:-----:|:-----:|
| Run 1 | 1603 | **568** | 1575 | 72.5% |
| Run 2 | 1271 | 0 | 1228 | 96.6% |
| Video | 1580 | 561 | 1524 | 71.2% |

### 阶段 2：eBPF 解释原因

`tracepilot.bpf.c` 在内核挂载 **13 个 tracepoint**（sched_switch / wakeup / binder / futex / cpufreq / mem_reclaim 等），以 v3 二进制格式落盘到 `events.bin`（450–690 MB）。离线分析时重算每个 jank 帧窗口内的 **runnable delay**（wakeup 到实际执行的时间差），回答"为什么会卡"。

| 会话 | events.bin | sched 事件 | enhanced 事件 |
|------|:--------:|:--------:|:-----------:|
| Run 1 | 690 MB | 5,859,276 | 522,760 |
| Run 2 | 459 MB | 3,958,504 | 365,290 |
| Video | 451 MB | 3,598,368 | 567,918 |

> **enhanced 事件**：BPF 采集的附加事件，含 binder 调用、futex 等待、CPU 频率变化、内存回收等，用于构建图依赖关系。

### 阶段 3：Graph 找关键路径

将全部事件构建为**交互关键路径图（Critical Path Graph）**：节点是线程（分类为 UI / Render / Binder / Futex / Video Decoder 等角色），边是因果依赖（SCHED、BINDER_CALL、FUTEX_WAIT、FRAME_DEPENDENCY、DECODE_DEPENDENCY、RESOURCE_STALL 等）。通过 **CriticalScore 加权评分**找到对 jank 贡献最大的线程，回答"谁是根因"。

| 会话 | 节点 | 边 | Top-1 | Top-1 Score |
|------|:---:|:---:|-------|:---------:|
| Run 1 | 6968 | 5234 | tid 103 | 0.825 |
| Run 2 | 4799 | 3106 | tid 16945 | 0.856 |
| Video | 6622 | 4992 | tid 103 | 0.746 |

### 阶段 4：Hint Engine 只做受控短时修正

基于关键路径分析结果和 Inference 推断，生成**短时调度修正建议**。每条 hint 携带 **TTL（300ms）**和 **rollback** 回滚策略，只修正而不永久改策略，防止过度干扰系统调度器。

| 属性 | 说明 |
|------|------|
| TTL | 300ms，到期自动回滚 |
| rollback | restore_nice / restore_uclamp_min / restore_affinity |
| 模式 | dry-run（离线分析时仅输出 hints.json + 审计日志，不真下发） |
| 3 种类型 | UCLAMP_MIN_TEMPORARY / BOOST_THREAD / PROTECT_UI_CHAIN |


| 会话 | hint 数 | 类型 | 目标 | TTL | rollback |
|------|:----:|------|------|-----|----------|
| Run 1 | 1 | PROTECT_UI_CHAIN | surfaceflinger (tid 686) | 300ms | restore_affinity |
| Run 2 | 1 | PROTECT_UI_CHAIN | surfaceflinger (tid 600) | 300ms | restore_affinity |
| Video | 0 | —（无线程满足 hint 生成阈值） | — | — | — |


> **核心设计原则：** Hint 不做长期策略变更，只做 jank 窗口内的受控短时修正；通过 TTL + rollback 确保不影响系统稳态调度。

**tid 48** 三次均出现在 Top-5。  
内核 RCU 线程（rcuop/4, rcuop/6）在 Run 1 和 Video 中占据高位，Run 2 中未被突出。

### 3.2 图特征对比

| 边类型 | Run 1 | Run 2 | Video | 视频 vs 页面切换 |
|--------|:-----:|:-----:|:-----:|:---------------:|
| BINDER_CALL | 52 | 53 | 45 | - |
| FUTEX_WAIT | 2371 | 1770 | 1977 | - |
| **RESOURCE_STALL** | 51 | 13 | **247** | **5–19x** |
| **DECODE_DEPENDENCY** | 567 | 0 | **560** | 视频特征（Run1 含后台解码） |

**关键发现：** 视频场景的 RESOURCE_STALL（247）是页面切换场景（13–51）的 5 到 19 倍。DECODE_DEPENDENCY 和 BUFFER_QUEUE 是视频场景独有的图结构特征。

### 3.7 启发式 vs 图方法对比（Task 12）

compare_heuristics() 对比图方法（CriticalScore 加权评分）与传统启发式（基于帧窗口重叠 + runnable delay P95 的经验公式）在 Top-K 线程识别上的重叠度。

| 指标 | Run 1 | Run 2 | Video |
|------|:-----:|:-----:|:-----:|
| 图方法 Precision@K | 0.50 | 0.70 | 0.60 |
| 启发式 Precision@K | 0.50 | 0.70 | 0.60 |
| Top-K 重叠线程数 | **5** | **7** | **6** |
| 图方法 SNR | 0.011 | 0.015 | 0.022 |
| 启发式 SNR | 0.500 | 0.500 | 0.500 |

**分析结论：** 图方法和启发式在 Top-K 线程识别上高度一致（Precision 完全相同），重叠数 5-7。图方法 SNR 偏低是因内核 RCU 噪声线程被误判为高关键度。建议加 --package 过滤目标 App 线程以降低噪声。

### 3.6 Jank 根因一致但场景差异显著

无论页面切换还是视频浏览，所有 jank 帧的根因均被分类为 **RUNNABLE_DELAY**。但图结构展示了两种场景的本质差异：

- **页面切换**：核心特征为 FUTEX_WAIT 密集 + UI 线程阻塞，无 Decode/Buffer/Network 边
- **视频浏览**：在 RUNNABLE_DELAY 基础上叠加了 DECODE_DEPENDENCY（560） + RESOURCE_STALL（247）+ NETWORK_WAIT（25）
