# Ray 多机批量推理任务说明文档

## 9. 选做：Ray 多机批量推理

### 9.1 方案概述

使用 Ray 框架将 20 个推理任务分发到多台 llama-server 节点并行执行，对比串行与并行的吞吐量差异。

**架构:**
- Ray Head: Mac (Apple M5, Tailscale IP: 100.101.168.109)
- Server 1: Mac 本地 llama-server (Metal, port 8080)
- Server 2: Legion 本地 llama-server (RTX 4060 CUDA, via Windows Tailscale 100.69.233.118:8080)

### 9.2 部署步骤

| 步骤 | 机器 | 命令 |
|------|------|------|
| 1 | 主机(Mac) | `ray start --head --port=6379 --node-ip-address=100.101.168.109` |
| 2 | 主机(Mac) | `./build-rpc/bin/llama-server -m model.gguf --host 0.0.0.0 --port 8080` |
| 3 | 从机(WSL2) | `./build-cuda/bin/llama-server -m model.gguf --host 0.0.0.0 --port 8080 --threads 8 -c 2048 -ngl 999` |
| 4 | 从机(Windows) | `netsh interface portproxy add v4tov4 listenport=8080 listenaddress=0.0.0.0 connectport=8080 connectaddress=<WSL2_IP>` |
| 5 | 主机(Mac) | `python3 ray_batch_inference.py --server1 http://127.0.0.1:8080 --server2 http://100.69.233.118:8080` |

### 9.3 测试结果

测试条件: 20 个 prompt，每个 max_tokens=128，4 种执行模式对比

| 模式 | 墙钟耗时(s) | 吞吐(req/s) | 生成速度(t/s) |
|------|-------------|-------------|---------------|
| 串行 (单台 Mac) | 21.7 | 0.92 | 106.5 |
| 单机并行 (ThreadPool-4) | 10.1 | 1.98 | 221.0 |
| Ray 轮询 (2台) | 1.2 | 16.29 | 1913.7 |
| Ray 固定分配 (2台) | 1.2 | 16.56 | 1923.8 |

> 注: 串行总耗时 = 各请求累加时间 (21.7s)，并行模式总耗时 = 批次墙钟耗时 (max)。生成速度 = 总生成 token / 墙钟耗时。

#### 各节点性能 (Ray 轮询)

| 节点 | 请求数 | 平均延迟(s) | 平均速度(t/s) |
|------|--------|-------------|---------------|
| Server 1 (Mac M5 Metal) | 10 | 1.102 | 106.77 |
| Server 2 (Legion RTX 4060 CUDA) | 10 | 0.738 | 158.94 |

#### 调度策略对比

| 策略 | 总耗时(s) | server1 请求 | server2 请求 |
|------|-----------|-------------|-------------|
| 轮询 (round-robin) | 1.2 | 10 | 10 |
| 固定分配 (前10/后10) | 1.2 | 10 | 10 |

**加速比:**
- 串行 → Ray 轮询: **18.1x** (21.7s → 1.2s)
- 串行 → 单机并行: **2.1x** (21.7s → 10.1s)
- 单机并行 → Ray 轮询: **8.4x** (10.1s → 1.2s)

### 9.4 分析

1. **并行效率**: 串行 21.7s → Ray 轮询 1.2s，加速比 **18.1x**。这一显著加速主要来自并发而非硬件扩展：串行模式下 server 逐请求处理（受 KV cache 限制），而并行模式释放了 server 的批处理并发能力。Ray 双机在此基础上进一步加速 8.4x（相对于单机并行），体现了多节点分担负载的价值
2. **单机并行 vs Ray 并行**: ThreadPool 单机并行耗时 10.1s，Ray 双机并行 1.2s，Ray 额外加速 8.4x。单机并行受单台 server 并发能力限制（4 个 slot 排队等待），而 Ray 将请求分散到两台独立 server，消除了排队瓶颈
3. **节点性能差异**: Legion RTX 4060 (158.94 t/s) 比 Mac M5 (106.77 t/s) 快约 49%，验证了 CUDA 后端在小模型上的生成速度优势
4. **调度策略**: 轮询和固定分配在 20 个 prompt 场景下性能几乎一致（1.2s vs 1.2s），因为请求量较小且两节点性能差异不大
5. **Ray 调度开销**: 20 个任务的调度开销可忽略（<0.1s），Ray Actor 模型有效避免了重复初始化开销。每个请求包含完整的 start_time/end_time/output_len 记录，便于后续分析
6. **扩展性**: 理论上增加节点可提升整体吞吐，但实际扩展效果取决于最慢节点的处理速度和网络带宽，需进一步实验验证

### 9.5 选做：并发压力测试 (5分)

在单台 Mac server 上测试不同并发度对性能的影响：

| 并发度 | 墙钟耗时(s) | 平均延迟(s) | P50延迟(s) | P95延迟(s) | 吞吐(req/s) | 生成速度(t/s) | 失败数 |
|--------|-------------|-------------|------------|------------|-------------|---------------|--------|
| 1 | 21.9 | 1.09 | 1.18 | 1.41 | 0.91 | 103.01 | 0 |
| 2 | 18.3 | 1.81 | 1.99 | 2.03 | 1.09 | 128.27 | 0 |
| 4 | 11.8 | 2.16 | 2.41 | 2.56 | 1.70 | 194.55 | 0 |
| 8 | 11.9 | 3.88 | 4.54 | 4.96 | 1.68 | 193.21 | 0 |

**分析:**
- **并发度=4 是最优配置**: 墙钟耗时最短 (11.8s)，吞吐最高 (1.70 req/s)
- 并发度=8 与并发度=4 性能几乎一致 (11.9s vs 11.8s)，说明 server 已达瓶颈
- 并发度=1 (串行) 墙钟耗时最长 (21.9s)，但单个请求延迟最低 (P50=1.18s)
- 并发度越高，单个请求延迟越大 (P50 从 1.18s 升至 4.54s)，这是推理引擎的典型特征
- 0 个失败请求，server 在所有并发度下稳定运行

### 9.6 选做：异构节点分析 (5分)

测试环境: Mac M5 Metal (server1) + Legion RTX 4060 CUDA (server2)，两台硬件配置不同

| 分配策略 | 总耗时(s) | 吞吐(req/s) | 生成速度(t/s) | P95延迟(s) | server1请求 | server2请求 |
|----------|-----------|-------------|---------------|------------|-------------|-------------|
| 轮询 (1:1) | 1.2 | 16.29 | 1913.68 | - | 10 | 10 |
| 按能力 (2:3) | 1.2 | 16.21 | 1875.20 | 1.23 | 8 | 12 |

**节点性能差异:**
- server1 (Mac M5 Metal): 平均速度 106.77 t/s, 平均延迟 1.102s
- server2 (Legion RTX 4060 CUDA): 平均速度 158.94 t/s, 平均延迟 0.738s
- server2 比 server1 快约 49%

**分析:**
- 两种策略性能接近（1.2s），因为请求量小且两节点性能差异不大
- 按能力分配让更快的 server2 处理更多请求 (12 vs 8)，但总耗时与轮询一致
- 在更大规模场景下，按能力分配会更有优势
- 异构环境下轮询策略已足够好，因为 Ray 的任务调度本身就能处理速度差异
